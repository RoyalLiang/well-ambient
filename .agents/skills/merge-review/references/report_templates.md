# 报告模板

两份模板：**内部评审报告**（给开发/审核者，落在 MR 评论或内部存档）和**客户交付版版本报告**（对外输出，客户视角）。按用户要求的受众选择；未说明时默认内部版。所有结论都必须遵守 `review_framework.md` 的证据与优先级规则。

---

## 模板 A：内部评审报告

### A.1 单个 MR / merge 提交

```markdown
# Merge Review: <merge subject>

- **MR/Merge**: <链接或 hash> by <author>, <date>
- **合并内容**: <源分支> → <目标分支>，含 N 个提交
- **变更规模**: X files, +A/-B
- **评审范围**: 以 MR 描述声明的改动为主线

## 结论
<通过 / 有条件通过 / 需修改后重新评审，一句话理由>

## 逐条核对 MR 声明的改动   ← 描述有条目时必须有（表格）
| # | 声明的改动 | 实现核对结果 |

## 阻塞问题（必须修复）
1. **[P0/P1] 命令式问题标题 — 文件:行号**
   触发条件、最小源码证据、实际影响、根因、具体修法和建议验证。

## 建议改进（不阻塞）
1. **[P2] 命令式问题标题 — 文件:行号**
   触发条件、最小源码证据、实际影响、具体修法和建议验证。

## Nitpick（可选）

1. **[P3] 命令式问题标题 — 文件:行号**

## 待确认与证据缺口

只放缺少规格、业务知识、外部调用链或环境验证的事项，不把它们伪装成缺陷。

## 附：非本主题的搭车改动   ← 存在搭车改动时才有

## 覆盖与验证
- 已评审对象、引用和文件
- 实际执行的测试/构建/静态检查
- 未读取、截断或无法验证的证据
- 剩余风险
```

### A.2 批量（多 MR / 多模块 / 多范围）

批量评审 = 汇总表 + 跨 MR 一致性检查 + 每个对象一份 A.1 明细：

```markdown
# 批量 Merge Review：<主题>（N 个对象）

## 汇总表
| 模块 | MR/范围 | 主题 | 结论 | 阻塞数 |

## 跨 MR 一致性检查
- 接口契约对齐（字段/类型/新增必填项）
- 上线顺序依赖（谁先谁后，写进结论）
- 共享配置/开关/Redis key 命名一致性
- 同源分支分叉/重叠提交（同一仓库多个并行 MR 时必查）

## 明细报告
<每个对象一份 A.1>
```

## 模板 B：客户交付版版本报告

对外输出。原则：**业务语言优先，技术细节服务于可信度**——客户要看到"交付了什么、质量如何保障、怎么上线"，但修复详情要具体（有根因、有位置、有验证）才"有料"。

```markdown
# <产品名> 代码评审报告

**评审范围**：N 个模块、M 个 MR/范围，覆盖 <业务主线>
**评审方式**：<评审轮次> 轮递进式评审——逐行 diff 审查、跨模块接口契约核对、目标分支取证
**评审日期**：<date>
**总体结论**：<全部通过 / 有条件通过 / 需整改>

## 一、版本交付内容总览
按业务主线组织（不是按模块罗列）：每条主线一段业务语言说明 + 模块交付表。
独立修复/增强单独一张表。明确标注"已完成但不随本版本合入"的内容，避免预期错位。

## 二、评审结论汇总
| 模块 | MR | 结论 | 发现问题数（阻塞/建议） | 状态（全部闭环/遗留） |

## 三、评审发现与修复详情（核心部分，必须有料）
每个重点问题一节：
- **发现轮次 / 位置（文件:行号）/ 根因**（带关键代码片段或缺陷场景复现路径）
- **修复**（commit id + 修法说明）
- **评审价值**（如适用：为什么该问题只有跨模块比对/取证才能发现）
原始 bug 的根因分析可附代码快照存档。
建议级问题用一张处置摘要表收尾（建议 → 状态）。

## 四、工程质量亮点
并发安全 / 防御性设计 / 可观测性 / 审核响应质量 / 回归验证矩阵 / 风险兜底开关——
每条一句话，必须有证据（测试数、场景数、具体机制名）。

## 五、部署顺序与上线检查清单
- 顺序用代码块图形化表达（①②③…），注明每步的强制约束
- 检查清单用 checkbox，每条可执行可打勾（迁移、配置、依赖版本、流程图、坐标确认…）
- 回退预案：开关回退 / 版本回退手册入口

## 附录：遗留确认项
不影响上线、需业务侧知悉或后续跟进的条目。
```

写作纪律：

- 不出现内部评审过程黑话（第几轮、谁提的意见），但保留"意见→修复"的闭环追溯，这是客户感知质量的核心证据。
- 技术术语配中文业务语义（如"四级纯链"→ 车道级精细化配置）。
- 数字必须真实：测试数、场景数、点位数来自 MR 验证记录或实测，不编造。
- 部署顺序的每一条约束都要来自评审中实际发现的依赖，不泛泛而谈。
