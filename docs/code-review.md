# 使用代码评审中心

在 **任务跟踪 → 代码评审** 中选择已配置的 GitLab 仓库。新 Commit / MR webhook 到达后自动调用 Agent 并进入评审队列，无需选择历史变更或手动发起。仓库选择仅用于筛选记录与配置知识范围。

评审读取固定版本的实际 diff、变更前后源码和系统知识，先做工程分析，再由第二轮模型独立复核。报告保留代码版本、知识条目版本、模型和提示词版本。停止评审会取消本地执行，不发布评论；已经消耗的模型请求无法撤回。

## 为 FMS 配置明确的业务范围

展开 **仓库评审策略**：

1. 将 **业务领域** 设为 **FMS · 车队管理系统**。
2. 选择任务分配、堆场、船舶装卸、场内转运、交通控制或充电场景。
3. 在 **项目知识范围** 填入系统知识库 `project` 范围的准确标识。
4. 确认知识库存在状态为 `active`、适用于该仓库或项目的业务规则。

检索只允许已启用的全局知识、当前仓库知识和指定项目知识。在这个范围内按代码变更、场景与知识内容匹配排序。仓库范围可匹配配置的 Project ID、仓库名称或路径；项目范围必须准确匹配所填标识。其他项目与归档知识不会进入提示词。

FMS 检查涉及任务/车辆身份、状态转换、完成证据、资源租约、重复/乱序消息、通信恢复、作业交接等，但这些检查项不自动成为系统的业务规则。具体业务结论必须引用实际检索到的知识。缺少项目或仓库知识时，报告显示 **部分评审**，不自动发送评论。

## 查看十个工程维度

报告分别分析业务与需求、健壮性、可复用性、抽象设计、封装与职责、并发一致性、安全权限、性能与资源、测试与可测性、交付与运维。

**问题与建议** 包含文件行号、逐字源码证据、触发条件与影响、修改建议和建议验证方法。源码行号、变更范围或知识引用不匹配的发现会进入待确认项，并阻止该报告自动发布。

**工程质量** 展示每个维度的判断依据，包括没有发现问题或无法评估的原因。打开评审详情后，弹窗默认显示只读 Markdown 评审正文。使用右上角的 **事实依据**、**代码依据**、**知识依据** 和 **规则依据** 查看来源信息；这些依据仍在同一个弹窗中切换，不会打开第二层弹窗。

“评审完成”表示评审流程完成，不代表代码无缺陷或获得合并批准。当前执行两轮模型静态分析及证据校验，不运行仓库代码、测试或构建，也不声称验证了未读取的跨服务调用链。

## 自动评审与评论同步

新事件自动评审始终启用（需要 GitLab 和 AI 服务配置可用），不受旧版 `auto_review` 值影响。先在列表上方选择一个具体仓库，再展开 **仓库评审策略**。两个评论同步开关按 GitLab Project ID 持久化，初始均关闭：

| 开关                 | 开启后的行为                                                      |
| -------------------- | ----------------------------------------------------------------- |
| 自动同步 Commit 评论 | 完整评审结束后，将报告同步到固定 Commit SHA 的评论                |
| 自动同步 MR 评论     | 完整评审结束后，确认 MR 仍打开且 base/head 未改变，再写入 MR 评论 |

评论包含评审总结、问题建议、各工程维度和覆盖限制。当前采用一条汇总评论，不创建行内讨论。

打开同步开关不会自动补发历史报告。开关保存期间会显示状态；保存失败会恢复服务器原值，避免页面状态与实际评论策略不一致。选中完整报告后，**按当前开关同步** 可主动处理该报告；该操作仍遵循仓库开关和版本检查。关闭开关不会删除已经发布的评论。

同一仓库、对象和代码版本共享发布记录，重复 webhook 或重新评审不会重复发评论。发送结果未知时保留状态，不自动重发；**核对远端评论** 只会核对已有记录。关闭、合并或版本变化的 MR 会显示版本失效状态。旧的“只分析提交说明”的 AI 评审入口已移除。

代码评审不会关闭或合并 MR，与已经暂停的 MR 自动关闭策略相互独立。

## 在线代码评审技能

生产代码评审不会读取开发机的 `.agents/skills`。线上运行规则保存在数据库的版本化 AI 技能表中，purpose 为 `code_review`：

1. 数据库迁移会创建并启用默认 `code_review` v1。
2. 全局超级管理员在 **配置中心 → AI 技能治理** 中建立新版本。
3. 代码评审技能必须先保存为草稿，再运行真实的两轮结构化评审验证。
4. 只有通过 JSON、十维覆盖、源码行号和知识引用校验的版本才能设为生效版本。
5. 新评审入队时冻结技能版本 ID、版本号、名称和内容哈希。之后启用新版，不会改变已经排队或历史评审。

在线技能只定义评审策略。非可信输入隔离、源码预算、权限、JSON 输出格式、两轮独立复核、证据校验和 GitLab 发布幂等仍由服务端固定实现，技能版本不能覆盖这些边界。

本地 `.agents/skills/merge-review` 仅供开发代理在仓库中执行人工评审流程，不是生产 worker 的加载来源。

## 最强大脑如何优化评审

`GET /api/strongest-brain/review-intelligence` 提供只读评审质量投影，按在线技能版本统计：

- 完整、部分、失败和运行中评审数；
- 高风险发现、待确认项和证据缺口；
- 人工重新评审率；
- 每个技能版本的完成率和异常分布；
- 当前生效技能的版本、哈希和验证状态。

最强大脑根据这些事实生成治理建议，例如补充仓库知识、沉淀重复缺陷规则、检查模型输出结构或建立下一版技能草稿。该接口不会自动修改、激活技能，不会重新评审，也不会发布 GitLab 评论。

## 权限和运行限制

- 队列和仓库列表需要全局 `dashboard:read`。
- 包含源码和系统知识的报告详情额外需要全局 `ai_context:preview`。
- 停止评审、修改开关和主动同步需要全局 `config:write`。
- URL 查询参数不能把这些全局检查降为单个仓库授权。
- 仅允许配置中的 GitLab Project ID。以 webhook 中的 Project ID 确定仓库，不按名称猜测。
- 单次读取最多 24 个变更文件，源码与 diff 总预算约 160 KB；知识最多 20 条、约 36 KB。超出代码预算、diff 被截断或源码读取不完整会显示部分评审，禁止评论同步。
- 自动入队处理 GitLab webhook 实际携带的 commits。GitLab 截断 Push Hook 的提交列表时，当前不回填未携带的提交；页面不提供历史补评入口。
- 进程中断后，超过 15 分钟仍处于运行态的记录会标记失败。打开失败详情并点击 **重新评审** 可创建新的排队记录；原失败记录保留为历史。
- GitLab/AI 服务必须已经配置并启用。应用会把允许范围内的源码与知识发送给现有配置的 AI 服务。

## 部署前迁移数据库

本次增加或扩展 `code_review_policies`、`code_review_runs`、`code_review_publications` 和在线 AI 技能版本字段，并接入项目现有数据库迁移流程。

在批准的部署环境中备份数据库，然后使用项目现有的迁移命令：

```sh
go run ./cmd/server --config /path/to/config.yaml --migrate-only
```

此命令运行整个应用的已有迁移流程，不仅迁移代码评审表。迁移后部署新后端及 `web/dist`，启动服务。最后在测试仓库检查知识范围和评审效果，再按需开启评论同步。

本次开发只使用隔离数据库、模拟 GitLab/AI 和认证浏览器验证。未迁移线上数据库、重启线上服务、调用真实模型评审业务代码，或向真实仓库发布评论。

## 设置评审规则

在代码评审页面展开 **评审规则**，可查看始终启用的十个默认工程检查项。在 **仓库补充规则** 中填写具体、可验证的要求，点击 **保存评审规则**。最多 8000 字符；清空并保存可恢复为仅使用默认规则。配置按 GitLab Project ID 独立保存，修改需要全局 `config:write` 权限。草稿不会自动保存，切换仓库时当前页面保留各仓库草稿。

补充规则用于后续新事件的两轮模型评审。已经入队的任务使用入队时的规则快照，报告内 **评审规则** 标签可查看当次补充规则。修改规则后，旧规则生成的报告不会同步到 Git；不会重新评审历史记录。默认证据校验、知识范围和十个工程维度不允许被补充规则取消。

本次新增规则字段需要随应用数据库迁移部署；仅更新前端不会使规则生效。

## 默认评审列表

页面默认显示所有已配置仓库的最新 200 条评审，按接收时间和 ID 倒序。列表使用生产级共享表格；点击首列的变更标题打开与“决策事项”一致的共享宽弹窗。窄屏会隐藏次要列，并把评论同步状态保留在首列摘要中，不需要横向滚动到末尾才能打开详情。

评审弹窗使用全宽只读 Markdown 文档面。切换 **评审正文**、**事实依据**、**代码依据**、**知识依据** 和 **规则依据** 时，弹窗外框保持相同尺寸，仅内容区滚动。同步评论、核对远端评论、重新评审和取消评审位于弹窗底部；操作成功或失败会直接显示在弹窗内，不会被遮罩挡住。关闭弹窗后，键盘焦点返回原来的变更标题。

作者来自 GitLab 原始提交或 MR 作者字段，保存到评审记录的 `author` 字段（升级需迁移）。旧记录无作者时显示“未记录”，不根据触发人猜测。
