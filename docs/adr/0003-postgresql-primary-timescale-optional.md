# ADR 0003：PostgreSQL 作为主库，TimescaleDB 仅作为可选时序扩展

- 状态：Accepted
- 日期：2026-08-26

## 背景

“最强大脑”同时处理两类数据：

1. Jira、发布、配置、人员、决策、证据链等需要事务、约束、权限、审计和跨实体关联的治理事实；
2. API 延迟、worker lag、队列深度、资源使用率、模型调用耗时等高频、追加式、按时间窗口聚合的观测样本。

把两类数据全部放进独立时序数据库会增加双写、一致性、权限、备份和跨库关联成本；继续只使用 SQLite 则不能满足生产并发、运维和扩展要求。

## 决策

生产主库使用 PostgreSQL。治理事实与业务状态继续使用普通 PostgreSQL 表。

首期不部署独立时序数据库，也不默认启用 TimescaleDB。出现以下任一可量化条件后，优先在同一 PostgreSQL 集群评估 TimescaleDB 扩展或原生分区：

- 单一观测表达到约一千万行并持续快速增长；
- 明确需要自动 retention、压缩、连续聚合或固定时间桶降采样；
- 经 `EXPLAIN (ANALYZE, BUFFERS)` 证明普通索引/分区无法满足已定义的查询 SLO；
- 数据为追加式观测样本，不参与核心事务状态机。

允许进入 hypertable 的候选是未来独立建模的 `observability_samples`、API/worker/模型耗时样本。`task_telemetries`、Jira/发布/配置版本、人员与授权、决策事件、数据资产证据不得仅因带时间戳就迁入时序表。

## 结果

优点：一个事务边界、一套权限/备份/监控，业务关联查询直接；未来可在不引入第二套数据库的前提下增加时序能力。

代价：高频观测量增长后需要主动做容量、分区和保留策略；托管 PostgreSQL 若不支持 TimescaleDB，则先使用原生按时间分区与聚合表。

## 验证要求

引入扩展前必须记录样本写入率、保留周期、查询形态、p95 SLO、普通 PostgreSQL 基线与运维支持情况。没有这些证据时，“使用时序数据库更优”不成立。
