# 最强大脑后续落地计划：排期、语料与人工干预

## 目标

本计划把三条链路收敛为可落地的产品与工程实施项：

- 需求排期后，用户能查看统一排期表、风险日历与延期预警。
- “上下文事实”重构为“系统设计语料库”，用于维护系统架构、功能边界、流程设计和估算口径，并由后台自动生成可缓存上下文包。
- “人工调停与干预 (Override)”从单点表单升级为可解释、可审计、可回滚的调停工作台。

## 1. 排期表与延期预警自动通知

### 现状判断

- 需求看板已有“待排期 / 已排期 / 进行中 / 已交付”泳道，排期动作会写入 `due_date`、`branch`、`task_group_id`。
- 通知中心已有 SSE 通道与通知列表。
- 当前延期预警更偏“任务创建多久未推进”的延迟信号，不足以覆盖“截止日临近 / 已超期 / 排期后无人推进 / 风险升级”的排期治理场景。

### 目标形态

- 在需求看板中新增“排期表”视图：按负责人、部门、任务组、截止日、风险等级筛选。
- 增加“交付日历”视图：以周/月展示需求和影子任务节点。
- 通知中心新增排期预警类型：即将到期、已超期、排期缺口、无人推进、二次延期。
- 飞书/系统内通知使用同一套预警事件，不做两套逻辑。

### 后端实施

1. 新增 `GET /api/schedule`：返回已排期需求和关联影子任务。
2. 新增 `GET /api/schedule/alerts`：返回基于 `due_date` 的风险事件。
3. 扩展通知计算：
   - `due_soon`：距离截止小于配置阈值。
   - `overdue`：当前时间超过 `due_date` 且未完成。
   - `stale_after_schedule`：排期后超过阈值无分支/MR/状态推进。
   - `reschedule_repeated`：二次以上延期。
4. 将预警事件接入现有 SSE，复用消息中心展示与已读机制。
5. 增加阈值配置：默认提前 1 天提醒，超期立即提醒，排期后 24 小时无推进提醒。

### 前端实施

1. 需求看板新增视图切换：看板 / 排期表 / 日历。
2. 排期表列：需求、负责人、部门、任务组、分支、截止日、状态、风险、最近活动、操作。
3. 通知中心对排期预警增加跳转链接，点击定位到对应需求。
4. 在卡片上统一使用风险徽标：未排期、即将到期、已超期、推进停滞。

## 2. 系统设计语料库与后台自动维护

### 产品定义

“上下文事实”不应被理解为某个孤立功能，而应是 AI 需求解构的系统参考资料层。用户维护的是：

- 架构设计：模块、服务、依赖、数据流、边界。
- 功能设计：已实现能力、不可触碰能力、复用入口。
- 流程设计：需求流转、评审、排期、开发、测试、发布流程。
- 估算口径：复杂度、风险、工时、人员能力、交付节奏。
- 历史样本：相似需求实际拆解结果、延期原因、验收问题。

### 后台链路

1. 资料接入：手工录入、Markdown/文档导入、GitLab README/API 扫描、Jira 历史样本。
2. 语料规范化：拆分为资料卡，保存类型、范围、版本、来源、维护人、置信度、token 数。
3. 语义索引：按标题、摘要、内容、范围生成检索索引。
4. 上下文压缩：需求解构前按需求文本、仓库、模块、需求类型选取资料，生成 context pack。
5. 缓存命中：context pack 使用 `scope + corpus_version + demand_fingerprint + model` 生成 cache key。
6. 自动维护：当资料源更新或需求归档完成，后台异步生成候选资料变更，进入人工审核或自动生效队列。

### 实施阶段

1. 第一阶段：重命名与解释 UI，保留现有事实卡模型，但对用户呈现为系统设计资料。
2. 第二阶段：新增资料导入接口与资料版本历史。
3. 第三阶段：接入后台异步语料维护任务，生成候选资料更新。
4. 第四阶段：需求解构归档反哺语料库，形成“评估 - 交付 - 复盘 - 语料更新”闭环。

## 3. Override 面板优化

### 现状判断

- 面板可执行强制指派、调整截止、挂起任务。
- 日期控件原先依赖透明原生 `input[type=date]`，视觉与系统不统一。
- 操作信息分散，用户需要在左侧诊断、右侧表单之间来回对照。

### 目标形态

- 自绘日期选择器，与需求看板日期体验一致。
- 在表单前展示当前负责人、当前截止日、风险等级。
- 将 AI 预案拆成“建议动作、影响范围、预计恢复时间、需要通知的人”。
- 每次人工干预生成审计事件，并展示执行结果：Jira 写回、飞书通知、SSE 广播、任务状态更新。

### 后续实施

1. 增加操作预检：提交前展示会影响哪些字段、通知哪些人。
2. 增加调停模板：转派协助、仅延期、挂起等待、升级会议。
3. 增加二次确认：高风险任务挂起或大幅延期需要确认原因。
4. 增加回滚入口：最近一次人工干预可回滚到上一个负责人/截止日。

## 验收标准

- 重新登录后，用户部门信息以 WellOS 恢复后的最新 profile 为准。
- KPI 不再作为顶层 tab，进入系统配置中的运营洞察区域。
- 系统设计语料库页面能让非研发用户理解“录入什么、后台如何使用”。
- Override 日期选择器不再触发原生控件视觉，且能正常选择、清空、提交日期。
- 排期治理计划明确前后端接口、通知类型与分阶段实现路径。
