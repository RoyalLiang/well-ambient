# 最强大脑架构演进与性能优化实施方案

本方案面向后端维护者，采用“先消除已证实的查询放大，再建立受治理执行与可信评价”的顺序。保留模块化单体、现有领域状态、数据资产账本和 DecisionPlan／Operation／Outbox；统一运行时首先接入真实代码审查流程。

前两批性能改造已经落地到当前工作树，未部署、未迁移业务数据库、未调用外部模型或写入 Jira。统一运行时、worker 隔离和可信评价仍是按依赖排序的后续工程方案，不能视为已经实现。

## 先交付不改变业务契约的性能收益

首批修改保留现有搜索排序、精确 Total、项目权限、详情内容和异步操作状态。没有通过限制结果总量或隐藏缺失记录来降低开销。

| 切片 | 原有成本 | 本轮实现 | 保留的边界 |
| --- | --- | --- | --- |
| 治理统计 | 每个 AgentRun 单独查询能力绑定 | 每批最多 500 个运行 ID，批量取得并按原运行顺序归集 | 现有指标口径、异常顺序和查询失败处理不变 |
| 方案目录搜索 | 全部命中 ID 和分数读入 Go，再截取一页 | 在数据库完成匹配排序和分页，只读取本页目录项 | 精确总数仍需要数据库处理完整匹配集合；深 OFFSET 尚未替换 |
| 方案比较详情 | 每条 comparison 分别查询 counterpart 和 proposal | 去重并分批查询关联记录，按原比较顺序重建详情 | 保留全部详情；大规模比较正文的解压与返回成本仍存在 |
| 目录补漏 | 全量读已发布资产，再逐条查目录和版本正文 | 固定本轮 ID 高水位，用 NOT EXISTS 排除已投影版本，按 250 条 keyset 分批，只读版本 ID | 补漏仍需检查发布资产；内存和关联查询受控，不代表数据库扫描完全恒定 |

对应实现：

- [治理统计](../internal/strongestbrain/intelligence.go)
- [目录搜索和详情](../internal/solutioncatalog/query.go)
- [目录补漏](../internal/solutioncatalog/module.go)

补漏只重建现有发布交接任务。处理中任务仍由原条件 upsert 保护；缺失版本继续返回错误及此前已排队数量；本轮高水位之后的新发布由正常事务 Outbox 或下一轮补漏处理。

## 用可重复的边界验证收益

本轮先让真实模块调用的性能契约测试失败，再修改实现。查询数和传回 Go 的行数是结构性证据，耗时与内存是本机微基准，不能外推线上收益。

环境：Apple M4 Pro，Go 1.25，内存 SQLite。治理基准每个运行有两个 bindings、20 次迭代；补漏基准每个规模 3 次迭代。不同夹具之间的耗时不可横向比较。

| 场景 | 修改前 | 修改后 |
| --- | --- | --- |
| 500 个运行的治理统计 SQL | 506 次 | 7 次 |
| 1,000 个运行的治理统计 SQL | 1,006 次 | 8 次 |
| 500 个运行的治理统计耗时与分配 | 8.406 ms；5.724 MB | 5.104 ms；2.119 MB |
| 1,000 个运行的治理统计耗时与分配 | 16.880 ms；11.315 MB | 10.008 ms；4.101 MB |
| 补漏：600 条已投影、3 条缺失的读取 | 607 次；最多一次物化 603 行 | 3 次；最多一次物化 3 行 |
| 补漏：10,000 条全部已投影的耗时与分配 | 134.160 ms；83.971 MB | 2.111 ms；约 15.5 KB |
| 搜索：10,000 条命中、20 条一页的物化量 | 10,020 行 | 20 行 |
| 搜索：同一夹具的耗时与分配 | 6.38 ms；1.44 MB | 4.89 ms；59 KB |
| 详情：128 条比较的 SQL | 260 次 | 6 次 |
| 详情：同一夹具的耗时与分配 | 5.84 ms；10.87 MB | 3.38 ms；9.06 MB |
| 详情：1,200 条比较、重复 counterpart 的 SQL | 2,404 次 | 8 次 |

目录搜索和详情基准每组 20 次迭代、运行 3 组，表内耗时为中位数。搜索采用窄 ID／分数子查询后再读取完整条目；宽行窗口的早期实验出现延迟退化，未保留该实现。

使用 Go 1.25 或更高版本，在仓库根目录执行：

```bash
go test ./internal/solutioncatalog ./internal/strongestbrain -count=1
go test ./internal/solutioncatalog -run '^$' -bench '^BenchmarkReconcileProjectedHistory$' -benchtime=3x -benchmem
go test ./internal/solutioncatalog -run '^$' -bench '^BenchmarkCatalog(SearchPage|DetailComparisons)$' -benchtime=20x -count=3 -benchmem
go test ./internal/strongestbrain -run '^$' -bench '^BenchmarkIntelligenceComputeReport$' -benchtime=20x -benchmem
```

新测试分别位于 `reconcile_performance_test.go`、`query_performance_test.go` 和 `intelligence_performance_test.go`。测试覆盖分批边界、空集、授权范围、排序与总数、完整详情、缺失关联、处理中任务和失败时的部分进度。

本轮验证已通过：

- `solutioncatalog`、`strongestbrain` 包回归与 `-race` 检查。
- server 的目录权限列表／详情回归、最强大脑能力完整场景回归。
- 独立静态审阅及 `git diff --check`。

没有运行生产负载或真实 PostgreSQL 验收；race 构建产生 macOS 链接器 `LC_DYSYMTAB` 警告，但测试退出码为零。前端没有改动。本机没有 yarn／Prettier，文档采用人工检查和链接结构检查，未声称运行格式化器。

## 第二批：PostgreSQL 汇总复用与一致性

已从官方 PostgreSQL 16.13 源码构建临时测试工具。测试自行创建合成数据实例，只开放私有 Unix socket，每次结束销毁实例；没有连接现有 DSN。此版本尚未与部署版本核对。

Daily Jira 现在复用同一授权范围、generation、数据库日期与时区的汇总。每个 Server／数据库保留一个 Reader，最多缓存 128 份汇总；列表仍从数据库读取。新数据、授权范围和日期变化会失效，旧日期／时区的游标返回既有 409 重载路径。外部事务中的读取不发布缓存，避免回滚后版本号复用导致错误。

测试还复现了 TRUNCATE 后版本不变、列表为空但汇总仍有值的缺口。现已补齐 generation 触发器的 TRUNCATE 事件、启用状态检查，以及读取前的 ACCESS SHARE 锁；普通行写入不被该锁阻塞。部署前必须执行现有读模型迁移，关闭自动迁移的实例会拒绝缺失新触发器契约的数据库。

在相同真实索引、合成数据及每组 100 次采样下：

| 稳定版本下的重复读取 | 修改前平均 / p95 | 修改后平均 / p95 |
| --- | --- | --- |
| 1 万事项，20 条一页 | 6.490 / 7.647 ms | 3.132 / 3.325 ms |
| 10 万事项，20 条一页 | 29.606 / 33.52 ms | 17.663 / 18.49 ms |

连续前后翻三页的汇总查询从 3 次降为 1 次。首次读取、新版本和新范围仍需完整汇总；列表执行计划仍有扫描和排序。上述数据是本机缓存命中场景，不代表线上或混合负载收益。

实现、复现命令、原始执行计划和验收范围见 [PostgreSQL 性能验证记录](daily-jira-postgres-performance-2026-10-04.md)。Daily Jira／readmodel／db／上一批两模块回归通过；Daily Jira、readmodel 和受影响 HTTP 测试的 race 检查通过。

## 继续验证 PostgreSQL 读路径与混合负载

已完成 Daily Jira 的 1 万／10 万条单客户端基线和执行计划；下面矩阵的混合负载、百万规模、部署同版本验收仍待完成。继续使用隔离合成数据，执行 `ANALYZE` 后保存实际 SQL、参数和 `EXPLAIN (ANALYZE, BUFFERS, SETTINGS, FORMAT JSON)`。

| 路径 | 数据矩阵 | 必须记录 |
| --- | --- | --- |
| 目录搜索 | 1 万／10 万记录，热门／冷门词，单／多项目，浅／深页 | 总数与结果一致性、返回行数、排序成本、Go 分配 |
| Daily Jira 列表和 summary | 10 万／100 万事项，负责人和项目倾斜、不同 bucket | page 与 summary 各自耗时、扫描行数、buffer、排序、p95/p99 |
| generation 更新 | 多项目并发写任务、评论和 commit | 版本行锁等待、写入 p99、无关更新导致的游标失效率 |
| API 与后台任务 | 并发读写、慢模型、积压任务 | 连接池等待、HTTP p95/p99、RSS、队列最老任务年龄 |

Daily Jira 每页重复汇总已得到缓解；下一步处理缓存未命中、频繁 generation 变化以及动态排序的成本。依据执行计划选择增量投影和索引，不直接照搬 SQLite 的读模型成绩。列表与 summary 仍共享明确的查询范围、授权和数据水位。

generation 仅在明确一致性语义后按数据依赖和 scope 拆分。缓存键必须包含授权范围、过滤条件、版本／水位与日期口径，不能以去掉游标校验换取表面性能。

测量方法依据：[PostgreSQL EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html)、[Go 诊断工具](https://go.dev/doc/diagnostics)。

## 让后台执行拥有独立资源预算

保留现有持久任务记录，分离目录同步、方案润色、比较与代码审查的并发预算。channel 仅用于唤醒，数据库记录仍是恢复依据。

在扩大 worker 数量之前，补齐领取租约、递增 fencing token、最终提交条件和取消传播。领取成功不等于旧执行者不会回写；约束必须覆盖结果提交。

验收场景：注入 120 秒模型延迟时，目录同步仍能执行；任务中取消能停止后续调用；租约过期后旧 worker 无法覆盖新结果；进程重启不会盲目重复外部写入。观察队列等待与执行时间，避免只记录总耗时。

## 用代码审查接通统一运行时

推荐保留 `codereview.Service.Enqueue/ProcessOne` 的调用方式，在内部加入固定步骤的受治理执行会话。通用运行机制负责冻结、授权、预算与调用收据；代码审查模块继续决定报告是否 completed、partial 或 cancelled。

执行顺序：

```text
入队并保存接收契约
→ worker 领取执行权
→ 受控取得代码与知识
→ 保存真实运行锁文件
→ 初审调用与收据
→ 冻结复核请求并执行
→ 领域模块校验、提交报告
→ 既有评论发布或决策流程
```

### 分层冻结实际输入

- 接收契约固定可信主体、真实业务归属、源目标、政策、Skill 和模型配置版本、预算上限。
- 取证完成后固定代码 head/base、知识来源、快照内容和 digest；取证本身也受授权与预算约束。
- 每次调用前保存最终请求及依赖输出。复核 prompt 包含初审结果，不能在初审前假装已冻结完整字节。
- 权限使用冻结上限与当前授权的交集，撤权仍即时生效；凭证只存引用。
- 历史记录缺少材料时标明 legacy/unsealed，GET 不生成伪装成执行事实的 lockfile。

过渡期只有一个实际能力版本来源。先绑定真实使用的旧 Skill，再验证 Registry 的 scope、依赖版本约束和预算后接管；不能让两套 active 记录独立决定同一次执行。

### 调用前预留预算，调用后保存收据

LLM Adapter 返回文本、provider response ID、实际模型标识、结束原因、usage 及其可用性。未报告用量不是零；计算费用、估算费用和账单确认费用分开表达。

调用前在短事务内原子检查剩余额度、预留预算并保存调用意图，提交后再访问网络；返回后先保存收据再交付结果。发生不确定结果时保留预留，不自动归零。初审、复核和允许的重试共享预算。

复用 `AgentRun`、bindings、events，补 owner、execution epoch、冻结内容、用量状态和租约信息；首批仅增加调用尝试账本。不引入第二套业务状态，也不让通用运行时拥有 Jira 发送队列。

### 明确恢复与重新评审

| 情况 | 契约 |
| --- | --- |
| 进程重启 | 继续同一冻结执行，复用已持久结果 |
| 失败步骤获准重试 | 新建 call attempt，消耗剩余额度 |
| 新代码、新模型重新评审 | 新建 execution epoch 和接收契约，保留旧证据 |
| 请求可能发出但结果丢失 | 标记 unknown，按调用类型对账；不盲重试 |
| 外部写入 | 复用 DecisionPlan／Operation／Outbox，远端确认仍由其负责 |

首个验收目标：初审结果已保存、复核期间进程重启后，不重跑初审，不重新选择模型、权限或上下文。并发预算、撤权、取消、收据落盘失败与过期 worker 提交都要进行故障注入验证。

观察模式只记录现有一次执行，不额外调用真实模型。启用强制治理后，迁移范围内不允许绕过运行时直接调用 provider。

## 可信数据到位后再扩大最强大脑的自动化

治理统计的窗口、分母、来源和质量定义需要单独修正。本轮只减少查询，没有把完成率重新解释为正确率，也没有把缺失用量解释为实测零。

真实评价闭环应包含固定样本、候选／基线配对、独立证据校验、人工采用／修改／拒绝反馈、受限灰度与回滚。当前 manifest 静态检查不能用作真实回放质量成绩。

模型、提示词或预算策略的变化，应同时比较证据有效率、错误建议、完成率、未知结果比例、延迟和每份有效报告成本。优化提案由后台任务生成，查询接口读取其结果。

## 按验收门槛推进，而不是一次性重构

| 顺序 | 交付范围 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1，已实施 | 查询批量化、搜索分页下推、补漏分批及对照测试 | 结果契约不变，查询／物化量下降，包回归通过 |
| 2，部分实施 | 已有隔离 PostgreSQL 基线、Daily Jira 汇总复用与一致性测试 | 继续完成混合负载、连接池等待、写入与未命中成本验收 |
| 3 | worker 资源隔离与恢复约束 | 慢任务隔离、取消、租约过期及重启验证通过 |
| 4 | code_review 统一运行时第一切片 | 调用前真实冻结、授权、预算及收据覆盖完整 |
| 5 | 指标口径修正与固定样本评价 | 质量和完成率分离，未知值明确，候选退化可检测 |
| 6 | 第二个业务接入及按需持久编排 | 多业务确有共同恢复、等待或并行分支需求 |

首批改造无 schema 变更；第二批需要重新执行读模型触发器迁移，不改变业务表字段。可以按具体修改回退，保留 TRUNCATE 触发器与旧读取代码兼容；不得回退整个脏工作树。后续运行时变更采用增量 schema，回滚只切换新运行路由，保留已接受契约、调用收据和未决费用。部署、生产数据迁移与外部模型对照运行均属于后续单独执行范围。
